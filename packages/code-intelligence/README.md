# `@nexus-brain/code-intelligence`

Provider-neutral code evidence for registered local Project v2 workspaces. The engine reads project identity only through `StateStore.getProject(project_id)`. Callers must select a stored `workspace_binding`; an injected platform resolver maps that opaque binding to a local path. Project v1, missing bindings, ambiguous bindings, or unresolved locations fail closed without scanning a workspace.

The engine offers `index`, `searchSymbol`, `getContext`, `getCallers`, `getCallees`, `getTests`, `analyzeImpact`, `getChanges`, and `health`. `getTests` uses CBM `trace_path` with `include_tests: true`; CBM marks test-related trace entries with `test: true` and does not promise a test file path in that response. Results always carry project/source/commit/index-version/coverage/confidence fields. Unknown coverage and confidence remain `null` or `unknown`; backend coverage checks never establish completeness. Code graph results are advisory and are paired with bounded direct-source or Git evidence. The direct-source search reports textual matches without claiming semantic call relationships.

The replaceable CBM adapter uses only the local one-shot CLI with argument arrays, no shell, bounded process timeouts, JSON output for query operations, and aliases derived from immutable `project_id` plus the exact opaque workspace binding location. The location is never normalized or returned; including it in the internal alias prevents two local workspaces in one Project from replacing each other's index. Every query filters by that alias, and the adapter does not enumerate CBM projects. Each indexing request may opt into cross-repository intelligence by explicitly selecting up to three registered target workspaces with their exact bindings. The engine resolves and indexes only those targets, then passes only their aliases to CBM's `cross-repo-intelligence` mode. It rejects self, duplicate, missing, ambiguous, unresolved, and over-limit selections. Target paths are redacted from results. CBM's cross-repository indexing response is a count summary, so the engine separately issues a read-only `query_graph` capped at 200 rows to retrieve `CROSS_*` relationships and emits a link only when a returned row explicitly names an allowed target alias or Project ID.

The engine requests only the `routes` aspect from `get_architecture`; CBM v0.11.0's default summary omits route details needed by the Windows fixture.

For each selected target, `related_targets` records its Project ID, workspace commits read before and after indexing/linking, CBM's reported index commit if present, and index generation read from `index_status` after cross-repo linking. Missing commit provenance stays `null` and generation stays `unknown`, with warnings. A link is returned only when the workspace HEAD was readable and unchanged across the operation, CBM reports a generation, and a bounded query row explicitly identifies the selected target. A cross-repository summary count alone never establishes a target link; otherwise the target's link is omitted and marked unattributed.

Before every CBM command, including health, the adapter executes `--version` and requires the exact `0.11.0` token. A mismatch or failed check blocks the CBM command. Results publish `backend_version` only after this check. The Windows CI fixture downloads and checksum-verifies the release archive and proves the cross-repository service link against a second local fixture; do not install CBM on a developer workstation as part of this package.

Unit tests run through the workspace CI `test:unit` step. The Windows runtime fixture is run separately by `test:cbm-integration` with `CBM_BINARY` set by the workflow.
