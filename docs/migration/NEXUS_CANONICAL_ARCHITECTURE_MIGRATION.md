## 3. Duplicações e fronteiras que exigem decisão/teste

1. **Redaction:** existem implementações parecidas, não comprovadamente equivalentes. Consolidar API, preservar wrappers antigos e provar por fixtures/testes de contrato antes de retirar uma.
2. **Tasks/scheduler:** `src/core.mjs`/`src/scheduler/*` são persistentes e locais; `operating-core/job-engine.ts` é in-memory; `workforce-scheduler.ts` é shift/wakeup; `cloud-fabric/workforce-orchestrator.ts` é execução provider-aware com evidência. Não são intercambiáveis. Definir modelo canônico, stores e adapters para não manter quatro autoridades.
3. **Routing:** roteador local de tool-risk, routers de modelo/IA, quotas de tenant e provider/resource/quota têm políticas diferentes. Uma pasta destino comum não autoriza uni-los em uma função.
4. **Dashboard:** servidor/UI MCG e dashboard snapshots de workforce são capacidades separadas. Um app control-center pode consumi-las, mas não se deve manter dois servidores ou duplicar APIs de relatório.
5. **Context/memory:** compilador/cache do MCG e context engine/memory kernel do Operating Core têm níveis e contratos distintos. Selecionar uma implementação canônica por domínio, com adapters, em ADR antes de apagar código.
6. **Registry source paths:** referências em `registry/*.json` apontam a caminhos inexistentes sob `packages/maestri-context-gateway`. Isso já afeta a exatidão do relatório; corrigir com mapeamento de source real, sem falsificar estado de disponibilidade.

## 4. Regras de dependência-alvo

Direção permitida: `apps → packages`; `control-plane → contracts, brain, execution, routing, providers, evidence, governance`; `execution → contracts, providers, evidence, governance`; `routing → contracts, providers`; `providers → contracts`; `brain → contracts, evidence` somente se evidence não importar brain; `evidence → contracts`; `governance → contracts`; `context-gateway → brain, contracts, evidence`; `edge → contracts, context-gateway/SDK HTTP-MCP ports`, sem importar stores autoritativos do cloud control-plane.

**Bloqueio conhecido:** no `cloud-fabric` atual há referências cruzadas entre control-plane, execution, routing, providers e evidence. Nenhum pacote deve ser separado até extrair interfaces/DTOs para contracts e fazer o grafo ficar acíclico. Uma dependência de nível inferior nunca importa seu orquestrador/consumidor.

Para cada pacote: (1) adicionar/ajustar teste no destino ou teste de arquitetura; (2) observar falha relevante; (3) mover o menor conjunto coerente; (4) corrigir imports/config/exports; (5) rodar teste focado, typecheck, unit e checks de segurança afetados; (6) inspecionar diff, grafo, `git status` e compatibilidade; (7) atualizar o único Master Blueprint com evidência.
